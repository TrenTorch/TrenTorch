data/app_data — internal engineering reference

Reproducing a new question, end to end

Every question in the curriculum is four real files on disk, compiled into the app's data bundle by a build step. This page is the template: follow it exactly and any question you author will build, test and render the same way Q1 and Q2 do.

01Philosophy

Every operation mirrors its real PyTorch signature exactly: same argument names, same shape conventions, same optional keywords (bias=None, reduction=, and so on). Never a simplified stand-in signature.

Theory follows a fixed arc: first-principles intuition, then the rigorous derivation, then one closing subsection on how PyTorch actually implements the operation internally (kernel fusion, nn.Parameter, init schemes). That last part is context only. It is never tested, it exists so a student understands the operation is a real, production thing, not a toy.

The bar for a Submit suite: genuinely adversarial, not just "does it run." Edge cases, array hygiene (non-contiguous memory, read-only arrays, no in-place mutation), tests aimed at one specific plausible wrong implementation each, and at least one oracle test baked from a real offline PyTorch run. Before you trust a suite, deliberately break the solution and confirm it actually fails.

02Folder anatomy

Three numeric levels: section, track, question. The numeric prefix only fixes display order, it is stripped before the app ever sees an id.

data/app_data/ _load.py # shared test-only helper, see § Reusing solutions 01-classical-ml/ # section 01-linear-regression/ # track 01-hypothesis-function/ # question README.md starter.py solution.py tests.py 02-mse-loss/ 03-mse-gradient/ ... 02-classification/ 02-deep-learning/ 03-llm/ 04-vision-transformer/ 05-systems-optimization/

Section and track names (after the prefix is stripped) are kebab-case and match the tags used inside every question's README frontmatter in that track.

03The four files

Every question folder holds exactly these four, no more. Nothing else is read by the build.

README.md

Frontmatter plus Statement, Theory, Explanation in that fixed order. The one file a human opens first when browsing the folder on GitHub, and the only file the build parses for everything except code.

starter.py

Real signature, real docstring, body replaced by a short TODO and pass. What the student actually sees first in the editor. Never executed as-is.

solution.py

The oracle answer: real, runnable, minimal. Never shown to the student, used by the Run/Submit backend and imported by tests.py via _load.py.

tests.py

A real, directly runnable pytest file. Numbered on purpose so "Run" (first couple of tests) and "Submit" (the whole file) show the same deliberate order.

04README.md schema

A small, fixed subset of YAML, hand-parsed by the build script, not a general parser. Keep values plain. 

---
name: linear-regression-hypothesis-function
title: Hypothesis Function
tags: [classical-ml, linear-regression, forward-pass]
difficulty: Beginner
---

## Statement

Problem description, the contract only. Never the formula or the one-line answer.

## Theory

The theory, building on the previous question in the track. Ends with a
"how PyTorch actually implements this" subsection, untested.

## Explanation

Why the oracle solution is written this specific way.
Field Notes
name Full semantic id, section-track-question style, kebab-case.
title Human-readable, shown in the question list and IDE tab.
tags Flow sequence [a, b, c], matches the section/track kebab names.
difficulty One of Beginner, Intermediate, Advanced, Mastery.
The three ## sections must appear in exactly this order. The build fails loudly if one is missing or out of order rather than silently shipping a blank tab in the IDE.

05Build pipeline

You author real files. Nothing you write is the artifact the app actually loads.

Never hand-edit generated-curriculum.json. Edit the source files under data/app_data/ and re-run the build. It is regenerated output, not a source file.

06Adding a question, step by step

  1. Create the folder

    Pick the section/track it belongs to, and the next unused numeric prefix in that track: data/app_data/01-classical-ml/01-linear-regression/03-mse-gradient/.

  2. Write solution.py first

    Write the real, minimal, correct implementation before anything else. Every other file (starter's docstring, the tests, the Explanation section) is written against this, not the other way around.

  3. Write tests.py

    Numbered categories, adversarial by design. See § Writing tests.py below for the exact structure to follow.

  4. Run pytest against your own solution

    pytest data/app_data/01-classical-ml/01-linear-regression/03-mse-gradient/tests.py must pass. Then deliberately break solution.py (flip a sign, drop a transpose) and confirm the suite actually catches it. Revert the break.

  5. Write starter.py

    Copy the signature and docstring from solution.py verbatim, replace the body with a short TODO comment pointing at Theory, and pass.

  6. Write README.md

    Frontmatter, then Statement (the contract, no formula), Theory (intuition, then rigor, then the untested "how PyTorch really implements this" close), Explanation (why the solution is written the way it is).

  7. Register the slug in questions.ts

    See § Registering the slug. Skip this and the question exists on disk but the IDE has nothing to link to it.

  8. Build and verify

    See § Build and verify for the exact command sequence and what "done" looks like.

07Writing tests.py

Fixed order, every time, so "Run" and "Submit" agree on what "the simple version" means. Group with comment banners, number every test function.

Order Category Catches
1–2 Basic correctness Wiring bugs. These two are what the "Run" button samples.
next Shape / general-case coverage Off-by-one in axis handling, wrong dimension assumed fixed.
next Parameter handling (bias, reduction, etc.) Optional-argument branches skipped in the happy path.
next Edge cases Batch size 1, a single feature, extreme magnitudes.
next Array hygiene Non-contiguous slices, read-only arrays, accidental in-place mutation.
next Mutation-catching One test per specific plausible wrong implementation (a dropped transpose, a wrong-axis broadcast).
last Independent oracles A naive loop implementation, and a baked real-PyTorch reference case.

The oracle test pattern

Generate the reference values once, offline, with real PyTorch, and bake them in as literals so the test suite itself needs no torch installed to run.

08Reusing an earlier question's solution

Every solution.py shares the same filename on purpose, which means they collide if imported the normal way from the same pytest session. One shared, curriculum-wide loader fixes it. 

# inside 01-classical-ml/01-linear-regression/03-mse-gradient/tests.py
import sys
from pathlib import Path
sys.path.insert(0, str(Path(__file__).resolve().parents[3]))  # data/app_data/
from _load import load_solution

linear_forward = load_solution("01-classical-ml/01-linear-regression/01-hypothesis-function").linear_forward
mse_loss = load_solution("01-classical-ml/01-linear-regression/02-mse-loss").mse_loss
Always run the full suite (pytest data/app_data/), not just one question's file in isolation, before trusting a new track. A single shared _load.py is what makes cross-track imports safe. An earlier per-track copy of this file caused a real collision the moment two tracks' tests ran together, and only running everything together surfaces that class of bug.

09Registering the slug

A question folder on disk is not yet linkable from the IDE. It needs an entry in src/lib/data/questions.ts, the full roadmap structure separate from the compiled content. 

mkTrack(
  'Linear Regression',
  ['Linear Algebra'],
  [
    ['Hypothesis Function', 'Easy', 'linear-regression-hypothesis-function'],
    ['Mean Squared Error Loss', 'Easy', 'linear-regression-mse-loss'],
    // ...
  ]
)

The third array element, the explicit slug, must match the question folder's name field exactly. Without it, mkTrack derives a slug from the track name and title instead, and the IDE has no folder to find at that address. Leave the explicit slug off only for a roadmap placeholder that has no authored content yet, it will correctly render "not published yet."

10Build and verify

  • pytest data/app_data/, full suite, not just your new file
  • Deliberately break solution.py once, confirm the new tests actually fail, then revert
  • node scripts/build-curriculum.mjs, re-run after any content edit
  • npm run check and npm run lint, clean
  • Open the question in the local dev server and confirm the IDE tab, hints and Submit results render correctly
Never edit generated-curriculum.json by hand. It is the build's output. Edit the four source files and re-run the build script.
